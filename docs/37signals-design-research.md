# 37signalsのデザインと、Ply第二版の失敗を調べ直す

調査日：2026-09-09。第二版への評価「5点」「アラートとかその辺がAI Slop」を受けた調査。第三版の提案・実装仕様・承認記録ではない。

第二版では、参照先の色や部品を拾い、画面を作る判断を省いてしまった。検索の前にデモの注意書きを大きく出し、通常の下書きへ警告色を付け、入力に連動しないプレビューとチェック欄を並べた。これらは、利用者の仕事より「整ったUIの部品を見せること」を優先した私の判断だった。

今回の研究で見直したのは、配色の好みだけではない。何を主役にするか、いつ注意を求めるか、何を隠しておくか、そして触ったときの楽しさがどこから来るかである。

## 調査の範囲と証拠の扱い

以下を区別して読む。

- **実画面の観察**：このセッションでブラウザに描画した画面。Basecampは第二版を作る前の同日観察も含む。利用者名、メール本文、案件内容は本書へ転載しない。
- **公開実演・製作者の説明**：公式画像、マニュアル、設計過程、インタビュー。現在の機能と過去の設計事例を混ぜない。製作者の思想は、その効果が万人に実証されたという意味ではない。
- **第三者による評価・研究**：生成方法が明示されたUI比較と実験。対象・方法の範囲を超えて一般化しない。
- **Plyへの判断**：上記と実装を照合した私の批評。参照元やユーザーが個別に指定した仕様ではない。

| 対象       | 実際に確認した範囲                                                                                                   | 未確認・制約                                                                               |
| ---------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Basecamp 5 | ログイン済みホーム、プロジェクト、To-dos、未入力の追加フォーム、文書入力、メニュー、カレンダー。公式リマインダー画像 | 実データを変更してエラーや成功通知を起こしてはいない                                       |
| HEY        | ログイン済みImbox、新着なし、Go anywhere、空のThe Feed、Set Asideの常設トレイ                                        | 現在の暗い表示設定で観察。配色を全アカウントの初期設定とは扱わない。内容のあるFeedは未観察 |
| Fizzy      | ログイン済み活動画面とメニュー、公式サイトのボード画像                                                               | 個別カード詳細へのアクセスは自動承認レビューが拒否。回避せず、私的詳細の観察は行っていない |
| Writebook  | 公開マニュアルの本文画面と保存操作の公式GIF                                                                          | 自分で編集・保存した検証ではない                                                           |
| AI生成UI   | NN/gが公開した人間設計・UX Pilot・Boltの比較画像、Boltの注釈画像、方法・プロンプト                                   | UIコードの実行や利用者テストは今回行っていない                                             |

## 1. Basecamp 5：プロジェクトの中身が画面を作る

ログイン済みプロジェクト画面では、中央の白い作業面に、太い左揃えのプロジェクト名が置かれていた。その上の細い領域には参加者・状態・操作がある。下の道具群は、見出しの色に共通性がある一方、中身が違う。To-dosには進行状況、ファイルにはファイル、チャットには発言、カレンダーには日付が見える。**同じカードの説明文を変えたものではなく、それぞれの道具の縮小された姿**になっている。

To-dosを開くと、一覧・チェックボックス・追加操作が中心になる。新規追加は一覧の場所に開き、補助項目が本文と同じ強さの箱を重ねる構成になっていない。文書入力では、タイトルと書く空間が中心で、公開対象の設定は別のまとまりに置かれる。カレンダーでは横の広さが必要になる。これらは同日の実画面観察であり、全画面の寸法・揃えを統一すべきだという根拠にはならない。

Basecamp 5の公式説明も、ホームの作成・最近使ったもの・活動の配置、開閉できるNew For You、画面を離れず使うMy Barなど、仕事の継続を中心に説明している。[Basecamp 5公式紹介](https://basecamp.com/5)

Ply第二版は、この構成を「薄紫の背景＋白い面＋色付きカード」に縮めてしまった。再利用したかったのは、道具ごとに中身を見せる考え方だったはずなのに、実装ではアイコン、上辺の色線、説明、クリーム色の小箱が反復される。手掛かりを増やすより、枠の種類を増やしている。

参照画像：[Basecamp 5の公式プロジェクト画面](https://basecamp.com/assets/images/screenshots/project-page.webp)。見比べる点はカードの角ではなく、各道具の中身の違いと情報密度。

## 2. HEY：分類、言葉、見た目、挙動が同じ考え方を表す

実際のImboxには、中央の太い見出し、紫の丸いWriteボタン、細いグラデーションの区切りがあった。Go anywhereを開くと、青から紫の強いグラデーション面に、Imbox・The Feed・Paper Trail・Reply Later・Set Aside・Bubble Upの入口が並ぶ。その下は小さな文字中心のメニューになる。

これは「紫、グラデーション、ピル型、タイルを使ったらAI Slop」という見分け方への反例である。色の有無だけでは評価できない。同時に、HEYで成立しているからPlyへ同じ部品を置いてよいということにもならない。

### 同じ空の画面でも、求めることが違う

| 実画面             | 見えた表現                                                                 | 私の読み取り                                                         |
| ------------------ | -------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Imboxの新着なし    | 小さなきらめきと短い一言。周囲に余白。既読領域はその下で続く               | 「今は対応しなくてよい」と伝えれば足りる。説明の読み直しを要求しない |
| 初期状態のThe Feed | 大きな文章、選択的な太字、重なる色の形。新しいメールが上へ来る読み方を説明 | 初めての概念を理解する必要がある。ここでは説明自体が主内容になる     |

この違いは「空なら同じEmptyState部品」という発想では出てこない。初回、作業完了、検索0件、通信失敗では、利用者の理解も次の行動も違う。

HEYの公式思想には、未読に戻すことで返信待ちを表すような代用を減らし、それぞれの仕事に専用の流れを用意するという説明がある。画面の個性は、その仕事の分け方から読むべきだった。[The HEY Way](https://www.hey.com/the-hey-way/)

### 楽しさを、警告色の追加で代用しない

Bubble Upの設計記録では、泡のイメージ、再浮上するという説明、Popという解除操作が一緒に検討されている。搭乗券を一度開いただけで奥へ流してしまうと困る、という具体的な利用場面から、明示的に解除するまで上部へ置く案が生まれた。アニメーションだけを最後に足した話ではない。[HEY Bubble Up: From kickoff to launch](https://updates.37signals.com/post/hey-bubble-up)

私の判断では、ここにPlyの「楽しくない」への重要な手掛かりがある。操作の名前が動きとつながる、置いた物がそこに残る、片付けた実感がある。第二版のアイコン付き補助パネルは、そのどれも増やしていない。

## 3. FizzyとWritebook：37signals全体を一つの外観へ畳まない

Fizzyの公式ボード画像には、横へ広がる列、折り畳まれた細い縦の列、内容の入ったカード、色の違い、人物、日付の印がある。カードは実際に移動・分類する対象である。紹介用の文章を囲うためにカードを選んでいるのではない。ログイン済み活動画面では、日付ごとの更新と画面下部のスタックが見えた。[Fizzy公式サイト・公開実演](https://www.fizzy.do/)

命名についての本人たちの説明も参考になる。初期のSplatは複雑な形で文字を載せにくくなり、形と名称が変わった。Fizzyという響きの楽しさは、概念の完全な整合性より選ばれている。**全装飾へ業務上の理由を後付けしない。楽しさにも価値はあるが、内容を邪魔する案は捨てている。** [Give it a name](https://37signals.com/podcast/give-it-a-name/)

Writebookの公開本文は、戻る・現在位置・全画面の操作を周辺へ置き、文字の大きさと段落で読む順序を作っていた。閲覧時の暗い表示を「Writebookは黒いデザイン」と固定しない。公式の編集GIFは明るい表示で、薄青の横長ツールバー、編集切替、書式操作、履歴、保存状態がまとまっている。本文の横へ別の固定プレビューは追加されていない。[WritebookのWritingマニュアル](https://enormicom-books.once.com/1/the-writebook-manual/6/writing-with-writebook)

保存は、マニュアルによれば未保存・処理中・保存済みを保存ボタンで伝える。毎回、本文の前に大きな成功ボックスを増やす構造ではない。公開GIFでチェック表示も確認した。[保存状態の公式実演](https://enormicom-books.once.com/u/autosave-ssql4x-Mw2LOm.gif)

| 比較軸     | Basecamp 5                       | HEY                            | Fizzy                          | Writebook                    |
| ---------- | -------------------------------- | ------------------------------ | ------------------------------ | ---------------------------- |
| 主役       | プロジェクトと複数の仕事道具     | メールをどう扱うか             | 状態を移るカード               | 書く・読む本文               |
| 面の使い方 | 道具ごとの内容を持つ作業面       | メール列、専用の置き場所       | 広いボードと列                 | 長く読む本文の領域           |
| 密度       | プロジェクト、一覧、編集で変わる | メール列は密、初回説明は大きい | カード情報は密、列を縮められる | 本文の行間と段落を優先       |
| 個性の表れ | 道具ごとの姿、進行の見え方       | 呼び名、トレイ、泡、色         | 色、カード、印、積み重なり     | 執筆と閲覧が近い、文字が中心 |

この表は観察の比較であり、優劣の採点ではない。同社の説明でも、HEYのスタックをFizzyなどへ展開するときは、位置や扱う情報を変えている。移植するのは発想であり、同じCSSの形を全製品へ押し込むことではない。[Making things that multiply](https://37signals.com/podcast/making-things-that-multiply/)

## 4. アラートを詳しく見る：重要なのは色より出現条件

まず、通知一覧、端末へのpush、入力エラー、操作後の確認、ページ内の説明は別物である。HEYのpush方針を、Plyのすべてのインライン表示へそのまま適用してはいけない。

| 事例                         | 発生理由・場所・扱い                                                                     | Plyを考える際の意味                                                      |
| ---------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Basecamp 5の予定リマインダー | 開始15分以内に画面下部へ小さく表示。近付くと緑へ変化し、会議リンクがあれば参加操作も付く | 色・出現時刻・場所・行動が結び付いている。「infoだから青い箱」とは異なる |
| HEYのpush                    | 初期状態では無効。相手・スレッド単位で選べる                                             | 発信側の都合で注意を求めない。ただしこれは端末通知の方針                 |
| Writebookの保存状態          | 書いている本文の前ではなく、ツールバー内の保存ボタンで伝える                             | 操作と結果を近付ける方法がある                                           |
| HEYの新着なし                | 短い文を通常の画面内に置く                                                               | 単に正常な状態を、大きな通知に昇格させない                               |

出典：[Basecamp 5のリマインダー](https://basecamp.com/5)、[HEYの通知方針](https://www.hey.com/features/notifications/)、[Writebookの保存](https://enormicom-books.once.com/1/the-writebook-manual/6/writing-with-writebook)。HEYはアプリアイコンの未読バッジを設けないとも説明しているが、これを「すべてのラベル・バッジを使わない」と読み替えない。

![Basecamp 5公式画像：主内容を保ったまま画面下部に小さく置かれた予定リマインダー](https://basecamp.com/assets/images/screenshots/event-reminder.webp)

上図は公式公開画像。カンバンの作業内容が残り、下端に次の予定が添えられている。Plyの検索の前にある横長のデモ説明とは、占める場所も発生理由も違う。

### 作り手の記録で、表面の模倣を検証する

**2012年のBasecampの通知設定**では、権限設定のUIを流用した結果、閲覧権限のない人にも通知できるように見え、毎回名前を入力する負担が生まれた。自分・全員への選択と、必要時に開く対象者チェックへ考え直している。似た部品を使えることは、同じ仕事をしていることを意味しない。[Design Decisions: Calendar Notifications](https://signalvnoise.com/posts/3148-design-decisions-calendar-notifications)

**2010年のHighriseの削除確認**では、「未分類になる」という抽象語を、影響を受けるタスク数と変更後の分類へ具体化し、重複する語を削った。派手な独自ダイアログを作る話ではなく、標準の確認UIの中で意味を明確にする仕事だった。これは過去のHighriseであり、現在のBasecamp 5の警告デザインを示す資料ではない。[Design Decisions: Refining alert text](https://signalvnoise.com/posts/2427-design-decisions-refining-alert-text)

別の設計思想との照合にはGOV.UKを使った。同Design Systemは通知バナー、本文の補足、入力エラーを区別し、バナーの多用を避ける。青い枠の通知も明確な用途を持って存在する。枠付きの通知そのものをSlopと断定する根拠はない。[GOV.UK Notification banner](https://design-system.service.gov.uk/components/notification-banner/)

Plyで先に決める必要があったのは、「この情報を、誰が、何の直後に、いつまで必要とするか」だった。色はその後の表現である。

## 5. AI Slopを、作者当てや禁止色の一覧にしない

本書で扱うAI Slopは、**文脈を詰めずに既成の見せ方を組み合わせ、見た目の完成度で判断の不足を覆ったデザイン**という評価上の呼び方とする。統一された学術尺度ではなく、生成AIで作られたという事実だけを指す語でもない。

制作過程を知らないサイトを、紫や角丸を理由にAI製と認定しない。逆に、人間が作ったものや37signalsの画面を、無条件に優れたものと扱わない。今回の比較には、生成過程が開示された資料を選んだ。

### 同じ課題、生成元が分かる比較

NN/gは、自社の研修受講者ページについて、AI生成と人間の設計を比較した。詳細な指示で近い構成になった例でも、Boltの出力は教材リンクと必要なパスワードが離れ、関連情報のまとまりが弱い。色や表示要素も競合している。一方、大まかな指示への出力はツール間で幅があり、「AIは必ず同じ見た目」という説明も正確ではない。[AI Prototyping in Real Design Contexts](https://www.nngroup.com/articles/ai-prototyping/)

参照：[人間設計・UX Pilot・Boltの比較原図](https://media.nngroup.com/media/editor/2025/10/17/1-prompt-2-vs-human-designs_6rb7ej2.jpg)。原寸でも確認した。人間側にも青い丸いボタンや淡い状態色がある。判定対象は部品の存在ではなく、情報と操作の関係である。

![NN/g公開資料：Boltの出力にある余白・まとまり・競合の問題](https://media.nngroup.com/media/editor/2025/10/17/4-nng-design-v-bolt.jpg)

この評価は2025-10-24公開。方法は専門家によるヒューリスティック評価で、広範な利用者の好みを測った実験ではない。方法資料にはプロンプト、比較条件、対象ツールがあり、CLI型のコーディングエージェントは対象外と明記されている。したがって現在のCodex全般の性能測定とも呼べない。[評価方法とプロンプト](https://www.nngroup.com/articles/testing-ai-methodology/)

独立した補助証拠として、CHI 2024の研究では、60人がチャットボットのアバターを発想する課題で、画像生成AIによる着想の固定化を調べている。AI条件で固定化が強まり、発想の数・多様性・独創性に不利な結果が報告された。ただし画像発想の20分課題であり、Web UIや今回のPlyへ効果をそのまま当てはめられない。私が採る教訓は、最初の案の装飾変更を続けて選択肢を狭めないことに限る。[The Effects of Generative AI on Design Fixation and Divergent Thinking](https://arxiv.org/html/2403.11164v1)

### 今回使う評価軸

以下は上記比較から作ったPly用の判断基準であり、AI検出器ではない。

| 観点       | 判断が省かれた状態                               | 判断が見える状態                             |
| ---------- | ------------------------------------------------ | -------------------------------------------- |
| 画面の主役 | UI説明、注意書き、歓迎文が作業より目立つ         | 対象と主要操作に、最初の視線と場所を渡す     |
| まとまり   | 全部を同じカードへ分配する                       | 一緒に読む・操作する情報が近い               |
| 色         | 下書き、補足、注意を手頃なtoneへ割り振る         | 色が示す差を、その画面で説明できる           |
| 余白       | 同じgapで全ての区切りを作る                      | 項目内は近く、仕事の切替は離れる             |
| 文章       | 画面を言い直す一般論、励まし、制作事情           | 対象、変更、次の行動を具体的に伝える         |
| 個性       | 汎用アイコンと淡色を加える                       | 対象の姿、言葉の調子、動きに製品らしさがある |
| 状態       | 通常・未使用・0件・失敗を色違いで済ます          | 理解や行動の違いを設計する                   |
| 完了判定   | 部品数・テスト数・生成画像数を品質の代わりにする | 実際の仕事を通して、見え方と操作を評価する   |

地味であれば合格という基準にもしていない。HEYの強いメニューやFizzyの色は、単に消すべきノイズではない。逆に、個性的に見せるために操作を遅くすることも正当化しない。

## 6. Ply第二版の、どこが具体的に失敗したか

実装と、保存済み1280pxの検索画面を照合した。以下は現在のコードを変える指示ではなく、不採用理由の記録である。

| 箇所                                                     | 現状と問題                                                                 | 参照から得た判断                                                                             |
| -------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| [notice.css](../src/css/components/notice.css)           | 既定で淡青の背景、全周の枠、左3pxの線。4toneとも同じ箱で、主な差が色だけ   | 文章の役割・寿命・操作との位置を設計する前に、汎用通知の見た目を固定した                     |
| [search.tsx](../catalog/pages/search.tsx)                | 検索欄の前へ、固定データだという長いNoticeを常設                           | デモの説明が最初の強い色面になり、検索を従属させている。説明は必要でも、この優先度は必要ない |
| 同検索画面                                               | 見出しの説明、キーワードの補足、固定結果の切替、結果見出しが順に場所を使う | 各部品だけなら整っていても、全体では探すまでにUIを読む量が多い                               |
| [editor.tsx](../catalog/pages/editor.tsx)                | 青い固定プレビュー、温かいチェック欄、公開設定、補足が並ぶ                 | 架空の業務を足して面を埋めた。入力内容の検討に役立つプレビューという期待とも食い違う         |
| 同編集画面                                               | 通常の「下書き」にwarningを指定                                            | 正常な制作途中の状態を、注意の意味へ寄せてしまった                                           |
| 同編集画面                                               | 保存結果の例をsuccessで見せつつ、実際には保存していないと説明              | サンプルであることは明示したが、模擬操作と結果を説明する都合が画面の中心へ入り込んだ         |
| [page-header.css](../src/css/components/page-header.css) | 任意アイコンを同じ黄色の角丸タイルへ入れる                                 | 読む画面、探す画面、書く画面を「アイコン＋大見出し＋説明」に寄せる癖を作った                 |
| [action-list.css](../src/css/components/action-list.css) | 色の上辺線、角丸アイコン、小さなプレビュー箱を反復                         | Basecampの道具ごとの実体を、汎用カードの装飾へ変換してしまった                               |

検索画面では、青い通知が横幅の大半を占める一方、利用者が欲しい記事一覧は画面のかなり下から始まる。Noticeの青を灰色に変えても、箱を角張らせても、この順序は直らない。

CSS・Honoの再利用性や表示試験の成功は、これらの判断を保証しない。第二版の試験結果は機能・規約・特定条件の表示確認として残すが、デザインの成功には数えない。

## 7. 前の方針から撤回すること

「37signalsらしさ」を、左揃え、クリームの補助面、青い操作、小さなSVGの組合せとして説明したのは不足だった。HEYは中央見出しを使い、Fizzyは広いボードを使う。一つの画面で見た配置を全体の原則へ昇格させない。

37signals本人たちは2023年のインタビューで、独立したデザインシステムより製品の既存画面を参照し、良い案があれば既存のやり方も変えると説明している。これは小さなチームでの本人たちの方針である。ユーザーが求めるPlyの再利用可能なCSS・Honoライブラリを廃止する根拠ではない。[Listener Questions / AMA、2023-03-29](https://37signals.com/podcast/listener-questions-ama/)

Plyでは、再利用する部品の都合から画面を逆算したことを改める必要がある。まず用途に合った画面と状態を見極め、その中で共有できる関係を部品へ戻す。通常・空・エラーを別に考える視点は、Getting Realにも明記されている。[Three State Solution](https://basecamp.com/gettingreal/09.3-three-state-solution)

## 8. 実装を再開する前に必要な、具体的な見方

新たな色指定や第三版はこの調査では作らない。次の設計を評価する際は、次の証拠が必要になる。

1. **同じ仕事で比べる。** 検索は検索、本文編集は本文編集として、参照画面とPlyを原寸で並べる。販売ページの見出しやトップページのカードを、入力画面の根拠にしない。
2. **一つの画面を状態まで追う。** 例として記事編集なら、通常、未入力、修正が必要、処理中、完了を描き分ける。新規未使用と検索0件も同じ説明にしない。
3. **各通知の文章から調べる。** 発生条件、対象、必要な行動、置く場所、消える条件を答えられない表示は、色を決める段階に進まない。単なる補足の可能性を検討する。
4. **楽しさを実物で確かめる。** 呼び名、対象の見え方、触った反応のうち何が良くなったのかを示す。「遊び心」「温かさ」などの形容詞だけで済ませない。意味のない演出を増やすことも避ける。
5. **部品化の前に画面を批評する。** 各部品が単独で整っているだけでは足りない。主要な仕事までの距離、情報の強弱、文章の量を画面全体で見る。

現時点の判断は、第二版は不採用、実装は停止。Basecamp 5を軸にする要求、独立ライブラリ、CSS単独利用、Hono SSR、stimulus-uiとの親和性、Hiragino優先という要件は維持する。次の外観を承認済みとは扱わない。
