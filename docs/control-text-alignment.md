# 操作コンポーネントの文字位置

2026-09-12、ユーザーの依頼により、繰り返した上付きの問題と採用した対策を残す。

## 問題と確認範囲

Button・Input・DatePickerなどで、文字が枠の中央より上に見えるとの指摘が繰り返された。個別の行高調整やコンポーネントの共通化だけでは解決を確認できていなかった。SSR・型・CSS検査の成功で作業を完了扱いにしたことが、見逃しを繰り返す原因になった。

今回の対策後、ユーザーは「Toolbar OK」と確認した。これはToolbarの受け入れ確認であり、他の全コンポーネント・全サイズ・全ブラウザを再確認したという意味ではない。Computer useは禁止されており、エージェントはブラウザ操作・Playwrightを実行していない。

## 技術的に確認したこと

CSSの行の箱が中央に配置されても、字形の見た目の中心が一致するとは限らない。行の上下位置にはフォントのascent・descentと行間情報が関係する。高さだけを変えれば安全なサイズにできる、と断定しない。[CSSの行高計算](https://www.w3.org/TR/CSS2/visudet.html#line-height)

このMacのCoreTextでHiragino Sansを計測した値は次のとおり。これはフォント情報の計測であり、ブラウザ表示の計測ではない。

| 文字サイズ | ascent  | descent | leading |
| ---------- | ------- | ------- | ------- |
| 14px       | 約12.32 | 約1.68  | 約7.00  |
| 16px       | 約14.08 | 約1.92  | 約8.00  |

確認したmacOS版WebKitの実装には、Hiraginoのdescentが3未満、lineGapが3以上の場合、descentを3へ増やしてlineGapを減らす処理がある。文字下側の領域を確保するこの補正は、字形と行の箱の中心がずれる要因になる。ユーザーのブラウザ名・バージョンは確認しておらず、全ての報告の直接原因をこの処理だけに断定していない。[WebKitの実装](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/graphics/coretext/FontCoreText.cpp#L155)

## 採用した対策

操作コンポーネントは[tokens.css](../src/css/tokens.css)の共通フォント定義を使う。

```css
--ply-control-font-family: "Helvetica Neue", Arial, var(--ply-font);
```

欧文フォントを先に指定して行の基準にし、日本語は従来のHiraginoへフォールバックさせる。本文用の`--ply-font`はHiragino優先のまま。新しいフォントの配布・読み込みは追加していない。

9月12日時点の適用先はButton／ActionLink、Input、InputGroupの入力枠、DatePickerのカレンダーパネル。FilterBar・Toolbarは共通Button／ActionLinkを利用するため、この設定を共有する。当時の最終対策では高さ・行高・上下余白を変更していない。

当時の[check-css.mjs](../scripts/check-css.mjs)は、4か所の適用先が`--ply-control-font-family`を参照していることを検査していた。一時コピーから各宣言を削除し、4か所とも検出されることを確認した。この検査は文字のピクセル位置を保証するものではない。

## 指摘を待たずに退行を止める仕組み

9月15日、DropdownMenuでの見逃しを受け、文書を読むだけの対策から通常の開発経路で失敗する検査へ変更した。

- [control-text.mjs](../scripts/control-text.mjs)は、共通Buttonのフォント・太さ・行高・中央揃え・上下余白を検査する。派生コンポーネントからの上書き、ラベルの子要素だけの移動、状態別・メディア条件内の変更も調べる。
- 操作用フォントのトークンを本文用へ戻す変更、`font: inherit`の再導入、独自の生のbuttonで共通コンポーネントを迂回する変更を検出する。既存の専用操作は所有元を限定する。
- DropdownMenuとTabsもフォント宣言の検査対象にする。DropdownMenuの文字指定はButtonを使い、説明文は別行にする。縦配置は下記のユーザー指定に従う。
- `vp run check`だけでなく、`vp run dev`と`vp run build`でも開始時に検査する。[Viteプラグイン](../scripts/control-text-plugin.ts)は読み込み・更新時にも検査し、起動済みサーバーでの変更もエラーにする。
- [回帰テスト](../test/control-text.test.ts)では既知の崩れ方を意図的に混入させ、拒否されることを検証する。実装を変更したら`vp run test test/control-text.test.ts`を実行する。
- [AGENTS.md](../AGENTS.md)を次回以降の作業開始時にも読み込む指示として置く。ユーザーの「上付き」という再指摘を確認開始の条件にしない。

### 基準の扱い

DropdownMenuは、その後のユーザー指定により上揃えへ変更する。項目をblockで上から積み、アイコン・ラベル・補助表記は先頭行に揃える。説明はラベルの下に置く。上下余白は「一行時の高さ − 行高 − 上下の枠線」の半分ずつとし、一行なら中央に見え、複数行なら同じ上端から下へ伸びるようにする。タッチ時も同じ計算で上下の余白を増やす。`align-items: center`で複数行全体を中央へ寄せない。この変更理由と対称な余白の指定を検査に反映し、中央配置・非対称な余白への戻しを回帰テストで拒否する。

基準は、ユーザー確認済みToolbarが使う共通Buttonの文字・縦配置である。色、横幅、横方向の余白、説明文のサイズを同一に強制するものではない。カレンダーの既存の行構造とタッチ用の高さは、検査内で宣言単位に区別している。これは全状態の表示承認を表す例外リストではない。

検査を通す目的で例外を増やさない。基準そのものを変更するときは、影響するコンポーネント、変更理由、既知の崩れ方を引き続き検出できる回帰テストを揃える。

### 検出できる範囲

この仕組みは、既知のソース上の退行を検出する。CSSの全カスケード、実際のフォールバックフォント、ブラウザが描く字形のピクセルを再現するものではない。静的検査の成功を「上付きの見た目まで確認済み」と報告しない。ただし、この限界を理由に、検出可能な退行をユーザーへ確認依頼して済ませない。

## 次の変更で守ること

- 新しいコンポーネントでボタンや入力欄を作り直さず、既存の共通コンポーネントと操作用フォント定義を利用する。
- `font: inherit`はfont-familyも上書きする。親が本文用フォントの場合、操作用フォントの基準を失わないか確認する。
- `text-box`、非対称padding、負の余白、文字のtranslateによる個別補正を追加しない。枠・余白・行高の所有箇所を確認し、二重加算を避ける。
- 再発時は共通フォントの適用・上書き・フォールバックを先に調べ、次に高さ・行高・上下余白・枠線の組み合わせを確認する。古い寸法調整を無条件に戻さない。
- SSR・型・CSS検査と、実際の表示確認を区別する。既存のスクリーンショット保存や要素の寸法測定だけでは、文字そのものの上下位置を検出できない。
- ユーザーが次のコンポーネントへ進むよう指示したら、その制作を進める。追加調査の質問や、比較ページの確認を進行条件にしない。

## 9月15日のButton・Inputの再修正

欧文フォントを先頭に置く対策だけでは不十分だった。今回の表示検証にはユーザーからブラウザ操作の明示的な許可があり、このMacのChromium・Firefox・WebKitで実際の描画を確認した。14pxの「日本語を確認する」は、WebKitでButtonが枠の中心より0.5px上、Inputが1px上に描かれた。32pxの枠や行高が合っていても検出できなかった問題である。

操作用フォントは同じローカルのHelvetica NeueとHiragino Sansに別名を付け、両方の行メトリクスをascent 89%・descent 11%・line gap 0%へ揃える。14pxと16pxで比較し、89%ではWebKitの両コンポーネントが中心と一致した。90%以上では16pxの位置が下へ寄ったため採用していない。字形・字幅・Buttonの高さ・行高・上下余白は変更しない。[フォントの行メトリクス指定](https://drafts.csswg.org/css-fonts-4/#font-metrics-override-desc)

```css
--ply-control-font-family:
  "Ply UI Latin", "Ply UI Japanese", "Helvetica Neue", Arial, var(--ply-font);
```

400と600〜900の太さを別のローカル書体へ対応付ける。InputとInputGroupは太さ400を所有し、親の太字を継承させない。フォントのダウンロードは追加しない。該当するローカル書体がない環境は従来のシステムフォントへフォールバックする。

[描画の回帰テスト](../test/browser/control-text.spec.ts)はCSSを読み込み、2倍密度の描画画像から字形の上下端を求める。14px／16px、Buttonの直書きと子要素、Inputの値とplaceholderを対象とする。このMacの3エンジンでは中心との差が0.5px以内になった。旧指定を再導入したWebKitでは1pxの上ずれを検出することも検証する。字形を含まない枠寸法の検査とは区別する。

このピクセル検査はHiraginoを読み込める環境が対象で、別OS・別フォント・日本語以外の全字形を保証しない。ローカル書体がない環境ではこの検査を明示的にスキップする。Windows・Android・iOSの実機は未確認。全体のデザインの受け入れ確認も、この修正や検査の成功とは別である。

## 9月27日の大きさの変更

HEY・Fizzyの実測に合わせて（[実測](references/hey-fizzy-20260927/README.md)）、Buttonの高さを32pxから36px（`calc(18em / 7)`）、largeを40px（`2.5em`）にした。文字は通常14px・large16pxのままで、検証済みの大きさから変えていない。一行Inputも同じ36px・40pxにし、上下の余白は「高さ − 行高 − 上下の枠線」の半分ずつを式で持つ。

途中で文字を16px・18pxへ上げる案を試した。largeを`calc(var(--ply-button-font) * 8 / 7)`のまま約18.29pxにすると、描画の回帰テストで字形の中心が枠の中心から1px下へずれた。ユーザーが普通の文字をFizzy並み（14〜16px）に戻すと決めたため、この案は採らず、基準も変えていない。

描画の回帰テストは、通常とlargeを幅240pxの見本で測る。大きい文字の案で、幅180pxではlargeの文言が2行に折り返して中心の比較にならなかったため、幅を広げた。判定の基準（中心との差0.5px以内、タッチ操作で44px）は変えていない。
