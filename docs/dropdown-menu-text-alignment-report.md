# DropdownMenuの文字が上付きに見える問題の再発レポート

作成日：2026年9月15日

## 結論

再開時のDropdownMenuには、既存の文字位置対策が適用されていない実装が残っていた。さらに、私は既存の注意事項を読んだにもかかわらず、フォント指定を1行追加するだけで確認に進み、文字の太さ・行高・余白・継承を含む差分を十分に照合しなかった。**既知の対策を部品全体へ適用する確認と、見た目の問題を検証する手順の両方が不足していた。**

ただし、適用漏れを修正した後にも指摘が続いている。**直近の上付きの直接原因を「共通フォントの指定漏れ」だけで説明することはできない。** 実際に描画されたフォントと字形の上下位置を採取・比較しておらず、最新の実装で問題が解消したとも判定できない。

## 1. 調査対象と証拠の範囲

次の資料を照合した。

- [以前の文字位置対策と注意事項](control-text-alignment.md)
- [再開時の引き継ぎ](../HANDOFF.md)
- 初期コミット`3332ed4`のDropdownMenu、共通CSS、検査スクリプト
- この会話内の変更内容と、ユーザー提供画像`Snapzy_2026-09-15_11-57-05_988.png`
- 現在の[DropdownMenuのマークアップ](../src/hono/dropdown-menu.tsx)、[CSS](../src/css/components/dropdown-menu.css)、[CSS検査](../scripts/check-css.mjs)

初期コミット、最初の1行修正、パターン拡充後の現行実装を区別して扱う。最初の1行修正は単独コミットではないため、その経緯の根拠は会話内の編集記録である。ユーザー提供画像と、その後の再発申告を、同一の描画版の証拠として扱わない。

本調査はソースと記録の照合であり、ブラウザ上の再現実験ではない。実際のブラウザ・適用フォント・拡大率・字形のピクセル位置は確認していない。

## 2. 何が起きたか

| 段階             | 実装・対応                                                                    | 問題点                                                                         |
| ---------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 以前の対策       | 操作用フォントを共通トークンにし、Buttonなどへ適用。Toolbarはユーザー確認済み | DropdownMenuを含む全操作部品の確認完了を意味していなかった                     |
| 今回の再開時     | 開閉用トリガーは共通Button、メニュー項目は独自の`button`                      | 同じ部品内で文字の指定経路が異なり、項目側に共通フォントが適用されていなかった |
| 最初の修正       | メニュー項目に`font-family`を1行追加                                          | 太さ・行高・高さ・余白・操作状態の差分を残したまま確認に進めた                 |
| 画像による指摘後 | カレンダーとの違いを受けてCSSを変更。その後、要求されたパターンを拡充         | 機能追加と文字位置の解決を別々に検証できていない。現行版の見た目は未検証       |

## 3. ソースから確認できる技術的な要因

### 3.1 共通部品を使っている範囲を取り違えた

再開時のDropdownMenuはトリガーだけが`Button`で、メニュー項目は直接記述した`button`だった。

項目のフォントは、[reset.css](../src/css/reset.css)の`font: inherit`を通して、[base.css](../src/css/base.css)の本文用フォントを継承する構造だった。共通Buttonに指定された`--ply-control-font-family`は、独自の項目ボタンには適用されない。

したがって、「トリガーに共通Buttonを使っている」ことを、メニュー全体で対策を共有できている根拠にはできなかった。ここは再開時の実装から確認できる適用漏れである。

### 3.2 最初の修正は文字の指定全体を揃えていなかった

最初の修正直後も、次の違いが残っていた。値はソースの宣言とトークンを対応づけたもので、ブラウザの実測値ではない。

| 指定        | 共通Button              | 最初の修正直後のメニュー項目   |
| ----------- | ----------------------- | ------------------------------ |
| フォント    | 共通の操作用フォント    | 共通の操作用フォントへ変更済み |
| 文字の太さ  | `400`                   | 共通base規則から`600`          |
| 行高        | `calc(10 / 7)`          | 共通base規則から`1.5`          |
| 最小高さ    | `calc(16em / 7)`        | `2.75rem`                      |
| 上下padding | `0`                     | `0.5rem`ずつ                   |
| 内容の配置  | `inline-flex`と中央揃え | 同じ配置規則を指定していない   |

メニュー項目をButtonと完全に同寸法にする必要がある、という意味ではない。**違いを意図して設計・確認する必要があるのに、フォント名の一致だけで対応を進めた**ことが問題だった。

画像に見られる太字・下線・矩形の背景も、既存カレンダーとの不統一を示していた。ただし、これらの違いだけから、字形が上へ寄る量や直接原因を確定することはできない。

### 3.3 現行版でも「Buttonを使ったから保証される」とは言えない

現行版では項目にも`Button`／`ActionLink`を使い、`.ply-menu`に操作用フォントを指定している。一方、`.ply-menu-item.ply-button`の`font: inherit`は、共通Buttonのフォント関連指定を親からの継承で置き換える。

現行の標準構造では、親のメニューパネルが操作用フォントを持つため、これを直ちに「本文フォントへ戻る不具合」とは断定できない。しかし、行高・太さも継承対象になる。Buttonの再利用だけでは文字指定の一致は保証されず、親から項目、項目内のテキストまで確認する必要がある。

また、現行版はラベルを`.ply-menu-text`で包み、説明文を持てる構造へ変わった。変更前と構造が異なるため、以前の確認結果をそのまま引き継げない。

## 4. なぜ検出・防止できなかったか

### 4.1 既知の注意事項を実作業の確認項目に落とし込まなかった

以前の記録には、共通部品の利用、`font: inherit`による上書き、フォント以外の高さ・行高・余白、静的検査の限界が明記されていた。今回、私はこの記録を読んでいる。

したがって、単に情報がなかったのではない。読んだ注意事項を、DropdownMenuのトリガーと項目それぞれへ適用して確認しなかったことが対応上の原因である。

### 4.2 CSS検査の対象と検査能力が足りなかった

再開時の`check-css.mjs`は、Button・Field・InputGroup・DatePickerの4か所を検査し、DropdownMenuを対象に含めていなかった。このため、DropdownMenuの適用漏れがあっても成功した。

現在は`.ply-menu`を検査対象に追加したが、検査するのは指定された規則内に共通フォント宣言が存在することまでである。CSSの最終的な適用結果、子孫での上書き、実際のフォールバック先、字形の上下位置は検証していない。

### 4.3 実行した検査が症状そのものを検証していなかった

SSRテストはHTML構造を、配置計算テストはメニューパネルの座標を、ビルドと配布検査は生成物を確認する。いずれも、項目内の日本語が視覚的に中央に見えるかを判定する検査ではない。

追加したブラウザテストも、主に操作・状態・パネルが画面内に収まることを対象にしている。ブラウザテストを実行しただけで、字形の上付きまで検出できる設計にはなっていない。

これらの成功件数を、今回の文字位置問題が解消した根拠に使うことはできない。

### 4.4 未確認の明記だけでは、修正内容の妥当性は補えなかった

今回は実画面が未確認であることを明記していた。しかし、それによって、既知の差分を残したままユーザー確認に出した問題が解消するわけではない。

Computer use禁止は確認手段の制約であり、再発の責任をユーザーの制約に帰す理由ではない。制約下でも可能だったソースの照合を十分に行い、「実装を変更した」と「見た目が直った」を分けて報告する必要があった。

## 5. 断定してはいけないこと

- **今回もWebKitのHiragino補正が直接原因だった**：以前の記録には関連する調査があるが、今回の描画環境との対応は確認していない。
- **フォント指定漏れだけが原因だった**：最初の1行修正後の申告を説明できていない。
- **`font: inherit`があるので必ず本文フォントに戻る**：現行版の親パネルには操作用フォントが指定されている。
- **高さやpaddingを揃えれば必ず直る**：行の箱と字形の見た目の中心を同じものとして扱えない。
- **機能パターンを増やしたので品質確認も完了した**：機能の対応範囲と文字位置の確認は別である。

## 6. 再発防止と解決の判定条件

| 必要な対応                                                         | 現在の状態・残る確認                                                       |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 項目にも共通Button／ActionLinkを使う                               | 実装済み。ただし専用CSSによる上書きまで含めて扱う                          |
| DropdownMenuを共通フォントの静的検査に含める                       | 追加済み。宣言の存在確認に限られる                                         |
| トリガー・通常項目・説明付き項目・サブメニューの文字指定を確認する | フォントだけでなく太さ・行高・余白・親からの継承を確認対象にする           |
| 文字位置の修正を機能拡充とは別に判定する                           | パターン数や操作テストの成功を文字位置の合格理由にしない                   |
| 問題が出た描画版で実際の字形位置を確認する                         | 未実施。対象版・描画環境・フォントの適用結果を対応づけて検証する必要がある |
| 解決を報告する条件を限定する                                       | 指摘された状態の日本語ラベルを確認し、解消を確かめた範囲だけを報告する     |

次の修正では、フォントの適用と継承を先に確認し、その後に行高・枠・余白・内容の配置を確認する。原因を確かめないまま非対称padding、負の余白、文字の移動で見た目を補正しない。

**本レポート時点で確定できるのは、初期の適用漏れと私の確認手順の不足である。直近の再発を起こした描画上の直接原因と、現行版での解消は未確定である。**
