# Ply 全体監査指示書

## 1. 目的と成果物

Plyを独立した立場で監査する。製作者の説明や既存テストの成功を結論にせず、現物・操作・ソースを照合して判断する。

目標は、**ClickUpの文字・余白・情報密度・操作の細部に、Basecamp／HEYの中央で仕事に向き合う構成と、少し楽しく親しみやすい手触りを備えた、汎用のデザインシステム**である。

メールクライアント、CRM、プロジェクト管理、ドキュメント管理、ファイナンシャルダッシュボード、チャット、管理画面からtoCまでを組み立てられるか評価する。

監査の成果物は次の3つ。まず監査結果をまとめ、製品コードの修正は次の工程とする。

1. 重大度順の指摘と再現手順。
2. 全対象の確認範囲と、未確認・不足の一覧。
3. 不要・統合候補・追加候補の部品と、その根拠・優先順位。

## 2. 開始時に確認すること

- `AGENTS.md`、`HANDOFF.md`、`package.json`と実行するscriptの本体を読む。
- ブランチ、HEAD、未コミット変更を記録する。実装の保存地点は `4f738c7`、その設計資料は `bbcd1ae`。監査は開始時の実際のHEADを対象とする。
- 最初に[文字位置の規約](control-text-alignment.md)を読む。「文字が上付き」は既知の不具合名として扱う。
- [設計方針](design-system-direction.md)、[前回の監査・検証記録](catalog-review-20260916.md)、[余白の全件説明](spacing-audit.md)、[移行資料](migration.md)を読む。**これらの記録自体の正確さも監査対象**。
- 参照画像と実測は[参照資料の案内](references/measurements-20260915.md)から確認する。参照製品の値、Plyの採用値、現在の実装値を分ける。
- ブラウザ権限はセッション冒頭のユーザー指示を優先する。末尾の貼り付け用指示に、ローカルPlyの表示検証の許可範囲を含めている。
- 前回の「OK」はその時点を保存してpushする区切り。全コンポーネント・全状態の品質承認とは扱わない。

## 3. 守る設計上の制約

- **サイドバーは禁止。上部中央のCommandMenuと中央の作業面を軸にする。** CommandMenuは独立した部品であり、単なるDropdownの置き換えではない。
- 特定のタスク管理アプリやダッシュボードのデモを、汎用ライブラリの完成の代わりにしない。
- Buttonの方向性はユーザーが肯定している。ごく薄いグラデーションと立体感を使える。色を変えるだけ、装飾や大きな余白を増やすだけで「楽しい」を達成したことにしない。
- `.ply-button`のように独立部品のrootへ接頭辞を付ける。内部の役割名は `.icon`、`.body`等とし、`.ply-button-icon`のような内部専用名を増やさない。独立したIcon部品の `.ply-icon`とは区別する。
- アイコンのサイズ・ウェイトを名前で特別扱いしない。chevronとcheckだけの分岐は禁止。SVGスプライトとCSS用SVGも同じ素材・共通規則で生成されるか確認する。
- Buttonの文字・縦配置は `button.css` が所有する。派生部品のfont shorthand、太さ、行高、上下余白、文字移動で辻褄を合わせない。チェックを通すための例外追加は禁止。
- DropdownMenuの複数行は上揃え。一行の中央は対称な上下余白で作る。項目全体を `align-items: center` で中央寄せしない。
- DropdownMenuを閉じる外側クリックが背後の操作を実行しないか確認する。現行の透明な実要素による受け方も監査し、document上のイベントキャンセルを増やして解決扱いにしない。
- コンテナクエリを使える。画面幅だけでなく、狭いペインや入れ子の作業面で成立させる。
- 操作要素のhover時にだけ下線を追加する表現を安易に使わない。意味・情報階層・状態の識別性と一緒に判断する。

## 5. 全体を横断する評価軸

### 造形と情報の読みやすさ

- 文字のサイズ・太さ・行高、本文と補足の比率、密度、罫線、角丸、影、アイコンの線と大きさが、役割に沿っているか。
- 同じ役割のリスト・操作・通知が、別々の人が作ったように見えないか。異なる値には説明できる理由があるか。
- 1pxの差も、フォントの字形・境界・余白の合計まで調べる。DOM矩形やCSSの行の箱が中央でも、字形が中央とは限らない。
- 「楽しい／退屈」を色だけで評価しない。押し心地、選択、片付け、読み進めるリズム、完了と失敗からの復帰が気持ちよくつながるか、実画面を根拠に判断する。
- 既存の数値や参考製品への似せ方を無条件に正解としない。守るべきユーザー指定と、現行実装を分ける。

### 余白とレイアウトの所有

- gap、margin、padding、insetの**実際の宣言を全件**確認し、余白の説明と照合する。条件分岐・上書き・計算値・既定marginも含む。
- flex／gridの選択、gap／margin-block-startの選択を、一次元・二次元の関係、折り返し、要素の有無、入れ子で説明できるか。
- 間隔を親子で二重に持つ、負の余白で打ち消す、特定の作例だけを固定寸法で成立させる実装がないか。
- 横と縦の間隔を同じにする必然性があるか。特にTagとFilterBar、ファイル行と他の一覧を比較する。
- 0件、1件、多件数、長い日本語、空白のない識別子、説明なし、複数行、狭いペインでも意味が保たれるか。

### 操作・アクセシビリティ・性能

- pointer、キーボード、タッチの操作と状態が対応しているか。hover／focus／active／disabled／busy／errorを確認する。
- 名前・説明・エラー・現在地・選択状態の関連付け、Tab順、矢印、Enter、Space、Esc、IME、閉じた後のフォーカスを実際に試す。
- 入力値、選択、外部formのsubmit／reset、取消、連続操作、失敗、再接続で状態が壊れないか。
- JSなし、forced-colors、reduced-motion、文字200%、実装が対応対象としているブラウザを確認する。見た目のUIが存在するだけで、操作対応済みとはしない。
- コピーや保存などの通知がレイアウトを動かさないか。再通知の重なり、読み切れる時間、通知を閉じる操作も確認する。
- 長いリスト、開閉、文字拡大、検索で不必要なDOM・描画・イベント処理が増えないか。時間切れを単にテスト時間の延長で隠さない。
- フォーカス管理、表示位置、状態、業務処理の所有が二重になっていないか。利用アプリが持つ通信・権限・永続化と、ライブラリの責任を区別する。

## 7. 汎用性と部品構成の判断

6種類のアプリについて、実際の作業を1つ以上想定して、部品をどう組み合わせるか検討する。大きな模擬アプリを作る必要はない。

- メール：一覧から読み、返信・宛先・添付・送信失敗を扱う。
- CRM：検索・絞り込み・属性編集・履歴・権限を扱う。
- プロジェクト：一覧／ボード／予定、担当・期限、並び替え・移動を扱う。
- 文書：階層・検索・プレビュー・共有・版の比較を扱う。
- 財務：期間、数値と単位、表・集計・差分・読込・欠損を扱う。
- チャット：履歴、入力、メンション、添付、送信状態を扱う。

部品の不足は「既存部品の組み合わせ」「既存部品の拡張」「独立部品の追加」に分けて判断する。統合・削除には現在の利用箇所と移行案を添える。抽象化やpropsの追加自体を価値としない。

`@tknf/stimulus-ui`の導入済みバージョンと全controllerを、配布型・実装・公開登録先から照合し直す。前回記録は0.1.0の38種類中15種類を利用・継承。UIのみ、native代替、独自実装、一部利用、未対応を区別し、同じ名前の部品があるだけで全契約対応と数えない。未対応controllerをすべて追加することも前提にしない。

## 8. 実行方法と証拠

- ソース調査は `rg` を使い、独立した検索・読取をまとめる。大きなファイルや同じ画像を無目的に読み直さない。
- 通常は `vp run check`、`vp run test` を基準確認にする。配布確認は `vp run build` の後に `vp run check:package`。生成前後のgit差分も確認する。
- ブラウザ検証は既存の `vp run test:visual <対象ファイル>` を利用し、仮説に必要な対象へ絞る。すべての部品の実表示は確認し、エンジン横断の詳細操作はリスクに応じて選ぶ。省略した範囲を残す。
- カタログは `/components`、個別は `/components/<id>`、全体は `/review/components`、分類別は `/review/components/group-0`〜`group-5`。必要なら `vp run dev --port 5179`。既存サーバーの有無を先に確認する。
- 広幅・375px程度・文字200%・狭いコンテナを確認する。ズーム方法、ブラウザ、viewport、DPR、入力状態を記録する。画面全体の幅だけでコンテナ対応済みとしない。
- 同じ失敗を無条件に繰り返さない。再現条件を固定して原因を切り分ける。テスト・検査基準を緩めて成功扱いにしない。
- **外部参照画像は保存済みのものを使い、ClickUp・Basecamp・HEYの再撮影で補わない。** 欠けた証拠は欠けていると記録する。過去の回遊や計測を実施したと捏造しない。
- ローカルPlyで新たに撮った画像は `docs/references/audit-YYYYMMDD/` に元のバイト列で保存し、画面・状態・取得日時・SHA-256を記録する。失敗画像は失敗と明記する。一時出力へ保存した画像も削除前に移す。
- 確認作業は分類ごとにまとめ、ユーザーへ見せる画像は指摘の証拠と代表状態を中心にする。画像を大量に出力することを監査の深さとしない。
- 元の製品コードと既存資料を保存した状態で監査する。必要な再現用実験は隔離し、実装を変えた後の結果を元の状態の証拠にしない。
- 秘密情報を読まず、データの送信や外部サービスの変更を監査の作業へ混ぜない。

## 9. 報告形式と完了条件

報告先：`docs/audits/YYYYMMDD-full-audit.md`。長い目録は同じディレクトリの別ファイルへ分けてもよい。

冒頭に、総評・優先して直す点・未確認範囲を簡潔に置く。各指摘には次を付ける。

- ID、重大度、対象、`ファイル:行`。
- 再現手順、データ／状態、ブラウザ／幅。
- 期待する振る舞い、その根拠、実際の振る舞い。
- 画像・寸法・操作結果などの証拠。
- 利用者への影響、根本原因の仮説、最小の修正方向、共通化すべき範囲。

重大度は影響で判断する。P1＝作業を阻害する／広範に設計目標を損なう、P2＝繰り返し現れる使いにくさ・不統一、P3＝局所的な磨き込み・説明の不足。「見た目の問題」だから軽微とはしない。未再現の仮説や好みの提案は、確定した不具合と分ける。

完了条件：

- 公開部品・CSS・controller・カタログの目録に漏れや黙った除外がない。
- 全部品の確認表があり、既知の懸念だけで監査を終えていない。
- 全余白の説明と実宣言を照合し、説明不足・不一致を特定している。
- 6種類のアプリへの適用と、不要・統合・追加候補を根拠付きで判断している。
- 前回の「修正済み」を再検証し、今回確認できなかったものは未確認と書いている。
- 機能・視覚・検査の結果を区別し、テスト件数だけで全体の品質を保証していない。
- 報告と証拠が保存され、次の修正を具体的に選べる。
