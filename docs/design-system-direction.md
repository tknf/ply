# Plyの設計方針

Plyは、メール、CRM、プロジェクト、文書、財務、チャットを組み立てるためのコンポーネントライブラリ。特定の管理画面やタスク管理アプリを成果物の代わりにしない。

目標はClickUpの情報密度と細部、Basecamp・HEYの中央で仕事に向き合う構成、その中で押す・選ぶ・片付ける操作が気持ちよく続くこと。サイドバーは採用しない。上部中央のCommandMenuを独立したコンポーネントとして持つ。

## ディテールの語彙

Plyは「何でも変えられる汎用の土台」を目指さない。全部を変えられるなら、デザインシステムとしての価値がない。Plyの価値は、ピル型のボタン、フォームの縁取り、破線の罫線のようなディテールを、意味と使う場所の決まった語彙として持つことにある。語彙があれば、Plyをそのまま使わないオリジナルのUIでも、人やAIが「この場面ではこのディテール」と判断して、統一感を保ったまま尖った表現を組み立てられる。

HEYは形の語彙が少なく、どの画面でも同じ使い方を繰り返すことで尖っていても統一されている（[実測と語彙](references/hey-app-20260926/README.md)）。Plyも同じ考え方を取り、HEYの見た目を写すのではなく、Plyの語彙を決める。

- 余白の段階、角丸、文字の段階、線の太さは語彙の土台であり、アプリごとに変えない。ここが変わると全部が別物になる。
- 語彙の一つ一つに「何を意味し、どこで使うか」を決める。同じ意味には同じディテールを使い、意味のない所では使わない。
- 色は語彙の中で役割ごとに持ち、アプリはその役割の中で色を選べる。

### Plyの語彙：重ねた紙と文具

Plyの名前（ply＝紙や板の重なり）に合わせ、語彙の軸を「重ねた紙と文具」に置く。Wingが作業面の後ろに紙を差し込むように、他のディテールも紙と文具の振る舞いから意味を決める。

| 波線                 | ここから新しい                                 | 未読や新着の始まり（Dividerの`line="wavy"`）                                                                                       | 装飾の区切り                       |

| 紙の短冊             | 一件ずつ手に取れる                             | DataList（リンクの行は指を載せると少し引き出す）                                                                                   | 表の行                             |

破線・波線・斜線・太枠・ラベルの太さはトークンで一つにし、コンポーネントごとに描き直さない。斜線は地を塗らず、面の上に一色の線だけを引く。斜線とミシン目は意味が違うので、同じ対象に重ねない。太枠は本文の色を面へ混ぜた淡い色にし、周りの1pxの線より目立ちすぎないようにする。

### 横断の規則

コンポーネントごとの都合で見た目を決めない。同じ意味には、どのコンポーネントでも同じ構造と同じディテールを使う（[HEY](references/hey-app-20260926/README.md)、[Fizzy](references/fizzy-20260926/README.md)の規則の作り方）。

1. **形**：同じ種類の部品は同じ形。押す物はピル。紙（作業面・Card・Boardの項目・Composer・メニュー・ダイアログ）は`--ply-radius-surface`（16px）、欄と作業面の中の面は`--ply-radius-field`（12px）、その内側の行は同心の`--ply-radius-control`（8px）、小さな札（チェックボックス・Keycap・Calendarの予定）は`--ply-radius-mark`（4px）、円は人と印だけ（手紙の差出人は切手の四角）。角丸と1pxの枠線を組み合わせた箱を作らない。Buttonは主・控えめ・危険の違いを塗り・枠・色で出し、形では分けない。
2. **紙と情報と欄**：
   - 紙（手に取れる物・書く物・浮かぶ物）は枠線を持たず、紙の影（`--ply-shadow-paper`、浮かぶ物は`--ply-shadow-menu`）で見せる。
   - 作業面に書かれた情報は枠で囲まない。一覧（DataList、ActionList、MessageList、TaskList、Comparison）は始まりと終わりの罫線と行の罫線だけ。Noticeは役割の色の面だけ。
   - 枠線を持つのは、書く・選ぶ欄と、意味のある線（ミシン目、枠に載せた見出し、Gridの罫）だけ。
3. **グラデーション**：二つの用途だけ。押す物（Button、選択肢、ページ送り、持ち手）には、分かるか分からないかくらいの縦の陰影（`--ply-fill-control`）で手触りを付ける。「ここを見て」の面（Notice、ErrorSummary、一括操作の帯、主操作）には、役割の色からその淡い対への135度（`--ply-emphasis-*`、`--ply-fill-primary`）を使う。一覧・本文・情報の面は平ら。
4. **状態**：
   - 現在地（今いる場所）は、インクの太字と青い2pxの印。縦の並びは開始側、横の並びは下に置く。Tabsは今のつまみの上端に置く。番号で並ぶ物（Pagination、Steps）だけは塗った円。パンくずの最後は並びの終わりなので太字だけにする。MessageListは太字を未読に使うため、現在地は印だけにする。
   - オン（切り替えた状態）は青い塗り。
   - 選択中（選んだ値）は淡い青の面。
5. **まとまりの見出し**：太字の名前、件数、右へ伸びる線、線の端の操作の順。件数は名前の直後に置く。Section、Boardの列、目次、Comparison、FieldGroup、Dividerで同じ形にする。
6. **項目の構造**：一覧の項目は「題名（太字）・補足・メタ情報」の順で、メタ情報は小さな文字を点で区切る。状態のBadgeと操作は末端に寄せる。Card、DataList、ActionList、MessageList、BoardのItemで同じ順にする。
7. **選んだ候補**：選んだ候補のチップは、どの入力でも入力の下に置く。

## 参照と採用値

[保存した実画面と測定値](references/measurements-20260915.md)を基準にする。元の画面で測った値と、Plyで採った値を分けて記録する。Button以外の造形の受け入れを、測定やテストの成功から推定しない。

| 役割                     | Plyの基準                                                            |
| ------------------------ | -------------------------------------------------------------------- |
| 一覧                     | 14px／20px、通常400                                                  |
| 入力ラベル               | 14px／20px、600（`--ply-label-weight`）                              |
| 補足・日時・局所的なタブ | 13px／20px                                                           |
| 小見出し・通常Cardの題名 | 16px／24px、600                                                      |
| ページ見出し             | 24〜28px、画面幅に連続して追従し、本文・操作コンポーネントと同じ書体 |
| 読む本文                 | 15〜16px、画面幅に連続して追従し、長文の行長を制限する               |
| Button・一行Input        | 32px、largeは40px。タッチ操作は必要箇所で44px以上                    |
| CommandMenu              | 幅480px、主要な入口4列または3列、検索、分類した一列の一覧            |
| 間隔                     | 補足4px、入力ラベル6px、関連要素8px、まとまり16px、セクション24px    |

文字に連動する値はrem・em・単位なし行高を使う。枠線の1pxを内寸へ二重加算しない。意味のない固定高で複数行を切らない。

## 形と触感

- 面・人物・分類・操作には別の形を与える。何でも同じ角丸のカードへ入れない。
- CommandMenuとNavigationの移動・操作の行は、共通の`--ply-radius-control`（既定8px）を使う。表示場所の違いだけでピル型と角丸矩形に分けない。
- Buttonはピル。主操作は役割の色の135度のグラデーションで塗り、控えめな操作はさりげない縦の陰影の面と枠にする。接地から遠方まで濃度を減らす影を使い、押したときに影が内側へ移る。文字自体は動かさない。
- 操作以外の情報を影で浮かせない。Tagはピル、Avatarは丸、完了は小さなチェックで示す。
- 角丸は横断の規則1の四つだけ。部品ごとの端数（3px・6px・9pxなど）を作らない。
- Plyの造形上の目安として、定型のCardやButtonは上下より左右に少し広い余白を取る。縦に読む親の面は左右より上下を広くし、下端に操作が来る面は上より下を少し狭くする。
- 見出しから本文へ流れる面は上端をやや広く、下端をやや狭くする。ただし、内容と配置を見て調整し、固定比率にはしない。
- 同じ対象の題名と補足は近付ける。行ごとに大見出しや長い説明を繰り返さない。全てを太字にせず、未読・現在地・見出し・入力や値の名前など意味のある所に使う。
- 青を主操作に使い、緑・アンバー・コーラルを明示した分類や状態へ使う。業務名や人物名から勝手に色を割り当てない。色だけで状態を伝えない。
- チェックの短い変化、見つけやすい現在地、すぐ隣の次の操作で手触りを作る。常時動く飾りや無関係なイラストを仕事へ重ねない。

上記の余白比はPlyの設計仮説であり、研究で定まった普遍値ではない。[共通領域による群化](https://www.sciencedirect.com/science/article/pii/001002859290014S)と[余白による区分の補助](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o3p10-whitespace/)を情報のまとまりに使う。一方、[視覚的な均衡と好みの実験](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2016.00335/full)から、単純な重心計算だけで好ましさを決めない。

## 文字位置

[文字位置の規約](control-text-alignment.md)をUI変更前に読む。共通フォントの89%／11%／0%の行メトリクスを保つ。Buttonはbutton.cssが文字・太さ・行高・上下余白を所有する。派生コンポーネントや子のspanから移動させない。

UI全体は同じローカル書体の組み合わせを使い、字間をnormalにする。読む本文は行高と行長で読みやすさを作る。Fontの追加配布は必要としない。

DropdownMenuは上揃え。一行時の中央は対称な上下余白から作り、説明が増えたら同じ上端から下へ伸ばす。DatePickerの月送り・クリアは共通Buttonの文字をそのまま使う。

## 構造と操作

- AppShellは上部中央の移動と中央の作業面。狭幅では左右の補助操作を別行へ移して中央を保つ。
- CommandMenuは背景を暗転しないnative popover。主要な入口と最近の場所などを分ける。検索中の矢印・Enter、通常のTab、Esc、起点への復帰を持つ。全体移動をDropdownMenuへ押し込まない。
- Dialogは判断が必要な処理、Popoverは対象の近くの補足、DropdownMenuは対象に対する操作。開閉とフォーカスの責務を分ける。
- Fieldは名前・説明・エラーを入力へ関連付ける。数値・日付・時刻の送信値と、表示上の補助は分ける。
- Grid、Flex、block、gap、margin-block-startの選択は[コンポーネント監査](component-audit.md#配置の一貫性)に従う。内部の役割名はルートから直下の関係で限定する。

## 提供する境界

`src/css`、`src/hono`、`src/controllers`を分ける。CSSと標準HTMLで使え、同じ構造をHono JSXでも出力する。必要なcontrollerを利用側のStimulus Applicationへ登録する。

業務の保存・認証・権限・通信・検索結果は利用アプリが持つ。カタログの試用処理をコンポーネントへ持ち込まない。追加候補と未提供機能は[コンポーネント監査](component-audit.md)を参照する。

確認は文字位置、状態と操作、狭幅と折り返しに分ける。静的検査、実ブラウザの寸法・操作、字形のピクセル検査、見た目の観察を別の証拠として扱う。
